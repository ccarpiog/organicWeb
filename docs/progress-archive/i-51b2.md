## What was built

- **Tile and grammar (decision):** one tile `éter` (kind `classWord`) in the «Grupos» row — design §15.2 names no row for it.
  It stands where the parent stands: `name = { prefix } , parent | { classGroup } , éter`. Its node is a parent node whose
  chain is `{type: 'classWord', tile}`, so the tree stays one shape and every walker of `tree.parent` works; the name-level
  prefixes before it are its two groups, parsed exactly as prefixes (a chain or ring ending in `il`, `isopropil`,
  `tert-butil`, `fenil`, a compound branch with prefixes of its own), one of them multiplied by `di`/`bis` when both are the
  same. `checkClassName()` keeps that shape: no locants or letter on a group (no parent to number), no one-atom group, no
  alkoxy group (`oxi`: the oxygen is the class word's), no `iliden`/`isopropiliden` (TILE_ORDER, each with its hint), and
  two groups in all (ETHER_GROUPS, «…solo pone uno», «…pone tres», or none). Numbers or a multiplier right before `éter`,
  `éter` inside a compound branch and tiles after it are TILE_ORDER with their hints.
- **Assembler (rule 7):** the groups are separate words: an automatic space between them and before `éter` (a `punct` piece
  with the role `space`, around which `separator()` writes nothing); `di-tert-butil éter` keeps rule 5's hyphen. Each group
  is enclosed as rule 5 encloses a prefix by itself (`isEnclosed()`: `(2-cloroetil) metil éter`, `bis(2-cloroetil) éter`,
  `metil (propan-2-il) éter`), never for its level (no crowded rule: `metil ciclohexil éter`). The engine's own class names
  (simple groups) are never enclosed, so they assemble exactly.
- **Tokenizer:** a space is read only right after a complete group (`il`, a retained word, `fenil`, END, a closed automatic
  mark) outside every mark; after it another group or `éter`, which ends the name.
- **Interpreter / builder:** a class name's NameSpec has the ether oxygen as its parent (ParentSpec kind 'ether', length 1:
  one atom, no carbon — `parentCarbons()` —, one heavy atom) and its groups as prefixes with one implicit slot each at the
  oxygen's only position (role `carbon`, domain 1…1), so `build()` attaches them as any prefix (`etherOxygen()`;
  `studentParent` is the oxygen alone, every `prefixAtoms` entry hangs from it) and `search.js` searches only the left-out
  locants inside a compound group. NameSpec `classWord` is `{kind: 'ether', text, tiles}`.
- **Verdicts:** the engine lists a class name only for the simple ethers (naming/index.js `etherClassAlternative()`), so the
  exact comparison makes those `alternative`; every other class name that builds is `otherName` (or `outOfScope` when the
  engine refuses the molecule: two rings, `symmetricEther`). `missingLocants` cannot happen for a class name: the engine
  writes none with numbers, so a filled text never matches.
- **Diagnosis (`diagnose.js`, header «Ethers»):**
  - `ETHER_SIDE` — when the parent rules give a parent-choice draft (RING_IS_PARENT, HYDROXY_PARENT, MORE_HYDROXY_GROUPS,
    LONGER_CHAIN, MORE_MULTIPLE_BONDS, MORE_DOUBLE_BONDS, MORE_SUBSTITUENTS, CHAIN_LOCANTS, CHAIN_ALPHABETICAL) and the
    student's chain shares no atom with the engine's parent with an ether oxygen on the path between them, `acrossOxygen()`
    tells it from the oxygen: it cuts the molecule in two sides, the parent is sought on one of them with the usual rules,
    why the other side wins (the replaced rule's own data, worded as the explanation's `etherSideReason()`), and the
    engine's prefix that holds the student's chain (from the naming's `prefix` parts: `metoxi`, `isopropoxi`,
    `ciclohexiloxi`). It keeps the replaced draft's trace rule and rule number (the kindest-reading comparison still works),
    opens «Reconoce el éter», adds the oxygen and its two bonds to the focus, and points at the student's prefix that holds
    the engine's parent; stripe and legend as for any parent choice («Tu anillo» when the student's parent is a ring).
    BRANCH_AT_END keeps its own message on the wrong side too (rule 1).
  - `ALKOXY_MULTIPLIER` — rule 7's `di` before an alkoxy prefix compound for its form only: a non-contracted prefix («un
    prefijo «-oxi» que no se acorta … es un prefijo compuesto (un grupo más «oxi»)»: `di(pentiloxi)`, `di(propan-2-iloxi)`
    in the pin style) and `tert-butoxi`, compound because its systematic form, «1,1-dimetiletoxi», has branches of its own
    (render.js `isCompoundPrefix()`); step `substituents` (it explains bis and the compound prefix).
  - The class names, a track of their own before every other rule (`classNameDiagnosis()`, compared with the verdict's own
    naming, which lists the class name): `CLASS_NAME_NONE` (the engine gives the molecule no class name; the message says
    for which ethers it does and gives the `-oxi` name; the `éter` tile), `CLASS_GROUP_WORDS` (the student's group words are
    not the engine's: `propan-2-il`, `1-metiletil`, `1,1-dimetiletil`, needless locants), `CLASS_DI` (a repeated group
    written twice or with `bis`), `CLASS_ORDER` (out of alphabetical order, `tert-` not counted with its hint, the plain
    word first on a tie). The right forms of CLASS_DI and CLASS_ORDER are assembled from the student's tree. All open
    «Reconoce el éter»; `student` is empty (a class name has no chain: no stripe, no legend).
- **Dialog / Ayuda:** the `éter` tile with its tooltip and the ending colour; the spaces in the name line are automatic
  `punct` spans. The Ayuda says the app writes the spaces too, and its ethers paragraph explains the class names.

## Decisions

- **`éter` as the parent position, the groups as name-level prefixes** (not a separate «group list» node): every group form
  (retained, ring, compound branch with left-out locants) parses, interprets, builds and searches with the existing code; the
  checks of `checkClassName()` keep out what an ether oxygen cannot carry.
- **The oxygen as a one-atom parent with implicit slots**, rather than rewriting the class name as a substitutive NameSpec:
  the student's reading stays the student's (the groups in tile order, the oxygen they hang from), and build/search need
  only `etherOxygen()` and `parentCarbons()`.
- **Enclosure of a class-name group by rule 5 alone, never crowded** — the app's own convention for names the engine never
  writes (`(2-cloroetil) metil éter`, `bis(2-cloroetil) éter`); it keeps the tokenizer's marks logic (START/END read from the
  marks) and the engine's simple class names unenclosed.
- **Verdict kinds:** a class name the engine lists → `alternative`; in another order / with other words / for an ether without
  a class name → `otherName` (a valid structure the app names); a molecule the engine refuses → `outOfScope`; a shape an ether
  cannot have → `invalid` (parser) and structural errors inside a group → `invalid` (builder).
- **`classNameOf()` mirrors `etherClassAlternative()`'s ordering** in `diagnose.js` (alphabetical without `tert-`, plain word
  first on a tie, `di` + word), since that function is internal to `src/naming/index.js`; the sweeps check it implicitly (every
  CLASS_ORDER / CLASS_DI requires the mirrored name to equal the engine's).
- **ETHER_SIDE inherits the rule number and trace rule** of the draft it replaces (`ruleOf()`), so the order of the R-3 rules
  and the kindest-reading choice are unchanged; DIAGNOSES lists the ether codes beside the rules whose place they take
  (ETHER_SIDE, CLASS_NAME_NONE, CLASS_GROUP_WORDS after PHENOL at rule 2; CLASS_ORDER after ALPHABETICAL_ORDER; CLASS_DI after
  UNGROUPED; ALKOXY_MULTIPLIER after MULTIPLIER_KIND).
- **«Ver el paso» of the class-name diagnoses opens «Reconoce el éter»**: no explanation step speaks of class names (and
  `src/explain/` is not changed: its snapshots stay); it is the step that says what an ether is and how the app names it.
  *Superseded by the review fixes below: they open a class-name step of their own.*
- **The deliberate null `di-tert-butil éter`** (the IUPAC form, with rule 5's hyphen): the engine writes `ditert-butil éter`;
  a message would have to call the student's correct form wrong or teach the engine's spelling. Written twice (`tert-butil
  tert-butil éter`) CLASS_DI quotes the assembler's `di-tert-butil éter`, never the engine's.

## Deviations / open risks

- None from the brief's requirements. Beyond them: ETHER_SIDE covers every parent-choice rule (P0–P4, N-rules, the ring and the
  OH ring/chain choice), with a property sweep asserting it fires exactly when the two chains lie on two sides of an oxygen.
- **Open question (forward engine, not changed): `ditert-butil éter`.** `src/naming/index.js` `etherClassAlternative()` writes
  `${multiplier(2)}${side}` without the hyphen before `tert-` that rule 5 and render.js write elsewhere (`di-tert-butil`), so
  the di-tert-butyl ether's class name reads `ditert-butil éter`. No tiles write it (the student's `di-tert-butil éter` is
  `otherName` with a null diagnosis); the closed loop asserts it is the only engine name it cannot read (the seeds give no
  such molecule). A fix belongs to `src/naming/index.js` (user's call; no fixture has the form).
- **Open question carried from I-51b1: `bis-tert-butoxi`.** The reverse engine still follows render.js, and ALKOXY_MULTIPLIER now
  explains it (the systematic form `1,1-dimetiletoxi` has branches). Should the user change render.js to `di-tert-butoxi`,
  remove the `tertButoxy` variant of ALKOXY_MULTIPLIER and `COMPOUND_RETAINED_ALKOXY` in `assemble.js`.
- The class-name messages and the Ayuda are new Spanish drafts (below); the class-name enclosure (`(2-cloroetil) metil éter`)
  is the app's convention, never compared with an engine name.
- design.md §15.8's Status column is not updated (the user's uncommitted file; the orchestrator tracks it in PROGRESS.md).

## Review fixes

The adversarial review (`docs/reviews/I-51b2.md`) found two SHOULD-FIX defects; both fixed in `src/reverse/diagnose.js`, no
change to `src/explain/` (no snapshot changed) nor to the UI code.

- **Class-name corrections opened a contradictory explanation** (`metil etil éter` → «Reconoce el éter», which says an ether
  «nunca va al final del nombre»). The four class-name codes now point at a step of their own, `CLASS_NAME_STEP`
  ('etherClass', «Monta el nombre con «éter»»), which `diagnosisExplanation()` inserts right after «Reconoce el éter»
