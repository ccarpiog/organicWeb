# I-19 — Undo after "Ordenar dibujo" (bug)

- Spec: `autoclaude/processed/190-undo-ordenar-dibujo.md`. Risk: routine. Worker: opus.
- Root cause: Deshacer always restored the coordinates exactly, in one step
  (also mid-animation, both targets, Chromium and WebKit). But when the ordered
  drawing did not fit, `animateCoordinates({fit:true})` called `centerView()`
  (zoom/pan) outside the undoable edit, so after Deshacer the hand drawing came
  back in the fitted view — zoomed and clipped, looking "not undone".
- Fix (`src/editor/{history,editor}.js`): history entries store the view
  before/after; `setCoordinates(positions, {view})`; edit/undo/redo events
  carry the view; `fittedView()` computed before commit, `applyEditView()`
  applies it. design.md §7 updated.
- Review should-fix (Codex): `applyEditView()` installed the normal-layout view
  over the 90° projection, clipping it. Fixed: while the projection is shown
  the saved view is held and applied once by `refresh()` when the normal
  drawing returns. E2E regression added (source + dist). Trade-off: a pan/zoom
  made in the 90° view after the undo is replaced by the held view on leaving it.
- Tests: unit history/core view round-trip; e2e draw → ordenar → deshacer →
  rehacer (+ Ctrl+Z), undo during animation (button and keyboard), 90° case.
  New e2e cases fail with the fix reverted.
- Out of scope: loading an example (Ejemplos) also recentres, and undoing the
  load does not restore the view.
- Verification: `npm test` 0 (411), `npm run check` 0, `npm run e2e` 0 (127).
- Review: Codex, ship-with-fixes, 1 should-fix fixed — `docs/reviews/I-19.md`.
