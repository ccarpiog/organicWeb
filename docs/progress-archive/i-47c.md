## Decisions (worker, accepted)

- A slot with a single possible value is never written into the filled text (`etinil`, not
  `et-1-inil`), as the engine never writes it.
- Left-out locants that fit nowhere → `invalid` with existing codes and new draft messages:
  `SAME_BOND` «No caben tantos enlaces múltiples…», `VALENCE` «No caben: pongas donde pongas…»;
  written locants alone overloading a carbon, or every placement too long → the usual build error.
- Old-style names with left-out locants stay old style when filled, so never match:
  `metil-2-buteno` → `ambiguous`. The old-style note rides every verdict except `invalid`.
- More than three names: three listed in search order (lowest locants first) + «u otra
  molécula» / «u otras N moléculas»; `candidates` keeps all.
- A `missingLocants` whose filled text is an alternative also gives the name the app gives first.
- Review fix: the drawn molecule is the cached, named graph; the student's reading is moved onto
  it (not the naming remapped — the naming cites ids everywhere, also inside `key` strings).

## Open risks

- R-4: two Kekulé drawings of a benzene will share the aromatic-equivalence key but are not
  isomorphic with bond orders — `placementReading()` would throw; `isomorphism()` must treat
  aromatic rings as equivalent then.
- A fully located name becomes `incomplete` only if its single naming overruns 1500 ms; its
  message («Faltan números») would then be wrong. Not reachable in practice.
