## Risks to probe
1. **Ordering vs. trap 1:** `showResult()` resets `arranged`/`ordered`; the ordered drawing (parent + locants highlighted, no redraw hint) must be registered *after* it. Check the parent highlight/locants really match what «Ordenar dibujo» gives, and that the layout registered is the one loaded (atom ids preserved by `loadMolecule()`).
2. **Canvas untouched on failure:** `canonicalLayout()` + `layoutProblems()` checked before any editor mutation; `loadMolecule()` outcome checked; non-drawing verdicts (`ambiguous`, `incomplete`, `invalid`, `outOfScope`) never touch the canvas.
3. **Undo semantics:** Deshacer after «Dibujar» restores the previous drawing and clears the verdict (chemical edit); a coordinate-only undo keeps result + verdict; redo; autosave stores the molecule only (verdict/tiles session-only). Any stale verdict surviving a later edit or a fresh «¿Cómo se llama?» is a bug.
4. **90° view:** `centerView()` must fit the displayed projection with the 90° view on; the worker also centres the new drawing where the old one was — check this does not fight `centerView()`.
5. **Verdict block correctness:** texts per §15.3 for `correct` (+ «También se llama …»), `alternative`, `missingLocants`, `otherName` (+ «Pulsa «Ver paso a paso»…»), old-style note; the added «Tu nombre: …» line (deviation from spec — judge whether it is reasonable). Escaping of user-assembled text into the DOM (no innerHTML injection from tile text).
6. **Accessibility:** announcement of verdict + name, focus return to «¿Cómo se dibuja?» on close, failure message announced, `aria-invalid` tiles.
7. **Test strength:** the layout-failure path is only unit-tested (e2e forces a refused load). Are the e2e tests asserting real state (canvas atoms, highlight, verdict text, undo) or just presence?
